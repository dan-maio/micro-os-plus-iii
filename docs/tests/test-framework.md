# How the µOS++ IIIe test framework works

*An analysis of the `xpack-development` branch of `micro-os-plus-iii`*

This document explains, in plain English, how the test framework of the
µOS++ IIIe portable library actually works: what the `package.json` files
contain, how **xpm** and **xPacks** fit in, how the **CMake** files are wired
together, and how a test is finally built and run.

It describes the state of the **`xpack-development`** branch (the branch where
all development happens, later merged into `xpack`). The reference commit used
while writing is `c47f806b` ("ci.yml update deps"). Where the `smp` branch
differs, this document is only about `xpack-development`.

> **The `smp` side.** What the `smp` branch changes in this framework (the
> port test builders, the board models, `tests-main.cmake` choosing the port by
> `PLATFORM_NAME`, `test_smpl/`, the SMP platforms and `test-smp-cmake`) is
> described in [`TESTS-XPACK-SYSTEM.md`](TESTS-XPACK-SYSTEM.md) and
> [`STEPS.md`](STEPS.md). The commits that take this branch to `smp`, one
> subject each, are listed in
> [`xpack-dev-smp.md`](../smp-integration/xpack-dev-smp.md) §15.4–§15.6 and
> Part III.

## 1. The mental model in one page

The whole strategy is easy to say and harder to implement:

> **Write the tests once, then compile and run the same sources with as many
> toolchains as possible, on as many platforms as possible.**

Everything in `tests/` exists to make that sentence true. The pieces are:

| Piece | Role |
|---|---|
| **Test sources** | Platform-agnostic C/C++ programs in `tests/sources/<name>`. Never modified per platform. |
| **Platform glue** | `tests/platforms/<name>/` — the linker script, the device, the CPU flags, and the command that launches the test. |
| **CMake** | Builds the images and registers each one with CTest. |
| **CTest** | Actually runs the tests and reports pass/fail. |
| **xpm** | The Node.js command-line tool that installs pinned tools, expands the build matrix, and runs named commands called **actions**. |
| **xPacks** | The packages (source libraries and binary tools) that xpm installs into `xpacks/`. |
| **`package.json`** | The manifest that declares the dependencies, the build configurations, and the actions. |

A single command such as

```sh
xpm run test-all -C tests
```

walks the whole matrix: it installs nothing new, but for every declared
configuration it configures CMake, builds the test images, and asks CTest to
run them.

## 2. Directory map

The framework lives under `tests/` in the repository root:

```
micro-os-plus-iii/
├── package.json                 # the library itself (the xPack being tested)
├── CMakeLists.txt               # builds the library target `micro-os-plus::iii`
├── include/  src/               # the portable library sources
└── tests/
    ├── package.json             # THE test manifest (deps, configs, actions)
    ├── package-lock.json        # npm lockfile for the JS devDependencies
    ├── CMakeLists.txt           # CMake entry point for the tests
    ├── cmake/
    │   ├── global-definitions.cmake   # which tests are enabled
    │   ├── common-options.cmake       # compile/link options common to all
    │   └── tests-main.cmake           # the orchestration script
    ├── sources/                 # the platform-agnostic test programs
    │   ├── rtos-apis/
    │   ├── mutex-stress/
    │   ├── cmsis-os-validator/
    │   ├── blinky/              # only on nucleo-f411re
    │   └── instrumentation/     # only on nucleo-f411re
    ├── platforms/               # the per-platform glue
    │   ├── native/
    │   ├── qemu-cortex-m0/
    │   ├── qemu-cortex-m3/
    │   ├── qemu-cortex-m4f/
    │   ├── qemu-cortex-m7f/
    │   ├── raspberrypi-pico/
    │   ├── nucleo-f411re/
    │   ├── nucleo-f767zi/
    │   └── nucleo-h743zi/
    ├── device-qemu-cortexm/     # generic QEMU device (vectors, startup, linker)
    ├── deprecated/              # old tests, kept for history, not built
    ├── xpacks/                  # GENERATED by `xpm install` (git-ignored)
    └── build/                   # GENERATED build folders (git-ignored)
```

Two directories are generated and never committed:

* `tests/xpacks/` — the installed xPack dependencies (source and tools).
* `tests/build/<configuration>/` — one CMake binary directory per
  configuration, plus a nested `xpacks/` with configuration-specific
  dependencies.

Both are listed in `.gitignore`.

## 3. xpm and xPacks

**xpm** is a portable Node.js command-line application. It complements npm
with features specific to C/C++ projects: it knows how to install source
libraries and pre-built toolchains, and it reads a special `xpack` section in
`package.json` to define build configurations and actions.

**xPack** is the package format. A source xPack is just a folder with a
`package.json` (with an `xpack` section) and some sources. A binary xPack is a
pre-built toolchain (compiler, QEMU, OpenOCD, CMake, Ninja, …) with a
`package.json` that describes where its binaries live.

Key concepts used throughout this document:

| Term | Meaning |
|---|---|
| **configuration** | One combination of platform + toolchain + build type, e.g. `qemu-cortex-m7f-cmake-debug`. Each has its own build folder. |
| **action** | A named command in `package.json`, run as `xpm run <action> --config <configuration>`. |
| **devDependency** | A package xpm installs into `tests/xpacks/` (top level) or into `build/<config>/xpacks/` (per configuration). |
| **build-helper** | The `@micro-os-plus/build-helper` xPack that provides the shared CMake functions and toolchain files. |

The minimum xpm version is declared in `package.json`:

```json
"xpack": {
  "minimumXpmRequired": "0.20.8"
}
```

## 4. The `package.json` files

There are two manifests that matter: the repository root one (the library
being tested) and `tests/package.json` (the framework itself).

### 4.1 The root `package.json`

This describes the `@micro-os-plus/micro-os-plus-iii` library:

```json
{
  "name": "@micro-os-plus/micro-os-plus-iii",
  "version": "7.1.0",
  "xpack": {
    "minimumXpmRequired": "0.20.8",
    "devDependencies": {
      "@xpack-dev-tools/clang": "21.1.8-1.1"
    },
    "actions": {
      "clang-format": "bash scripts/clang-format.sh",
      "cmake-format": "bash scripts/cmake-format.sh"
    }
  }
}
```

It contributes two things to the tests: the library source tree, and a pinned
clang (which also supplies `clang-format`) used by the two code-style actions.
The library package itself has no runtime dependencies: it is a monolithic
source library, and the platform-specific parts are added by the applications
(the tests) as separate xPacks. It is the package that consumers add with
`xpm install github:micro-os-plus/micro-os-plus-iii`.

### 4.2 `tests/package.json`

This is the heart of the test framework. It has four important sections:
`devDependencies`, `properties`, `actions`, and `buildConfigurations`.

#### devDependencies

```json
"devDependencies": {
  "@xpack-dev-tools/cmake": "3.26.5-1.1",
  "@xpack-dev-tools/ninja-build": "1.11.1-3.1",
  "@micro-os-plus/build-helper": {
    "specifier": "^2.17.0",
    "local": "link",
    "platforms": "all"
  },
  "@xpacks/arm-cmsis-rtos-validator": {
    "specifier": "github:xpacks/arm-cmsis-rtos-validator#v1.0.0-4",
    "local": "link",
    "platforms": "all"
  },
  "@xpacks/chan-fatfs": {
    "specifier": "github:xpacks/chan-fatfs#v0.13.1-5",
    "local": "link",
    "platforms": "all"
  }
}
```

These are the packages needed by *every* configuration:

* **cmake** and **ninja-build** — the build generator and build tool.
* **build-helper** — supplies the `xpack_*` CMake functions and the toolchain
  files (`gcc.cmake`, `clang.cmake`, `arm-none-eabi-gcc.cmake`).
* **arm-cmsis-rtos-validator** — the Arm CMSIS RTOS API validator used by the
  `cmsis-os-validator` test.
* **chan-fatfs** — the FAT file system used by the `rtos-apis` test.

The `"local": "link"` setting means xpm creates a symbolic link to the copy in
the central xPacks store instead of copying files; this makes development
faster and keeps a single copy on disk.

#### properties

Properties are string templates used by the actions:

```json
"properties": {
  "buildFolderRelativePath": "{{ 'build' | path_join: configuration.name | to_filename | downcase }}",
  "commandCMakeReconfigure": "cmake -S . -B {{ properties.buildFolderRelativePathPosix }} -G Ninja -D CMAKE_BUILD_TYPE={{ properties.buildType }} -D PLATFORM_NAME={{ properties.platformName }}",
  "commandCMakeBuild": "cmake --build {{ properties.buildFolderRelativePathPosix }}",
  "commandCMakePerformTests": "cd {{ properties.buildFolderRelativePath }} && ctest -V"
}
```

Notice that the build folder name is derived from the configuration name, and
that the platform is passed to CMake as `-D PLATFORM_NAME=...`. That single
variable is what makes the same `tests/CMakeLists.txt` behave differently for
each platform.

#### actions

Actions are named commands. There are two families:

* **Per-configuration actions** — `prepare`, `build`, `test`, `clean`,
  `install`, `link-deps`. These are defined inside the hidden build
  configurations and are run with `--config`.
* **Aggregate actions** — `test-ci`, `test-all`, `test-native-cmake`,
  `test-cortex-cmake`, `install-ci`, `install-all`, `clean-all`, … These
  call the per-configuration actions for many configurations in sequence.

Examples:

```json
"test": [
  "xpm run test-qemu-cortex-m7f-cmake"
],
"test-ci": [
  "{% if os.platform == 'linux' %}xpm run test-native-cmake-gcc{% endif %}",
  "{% if os.platform == 'linux' or os.platform == 'darwin' %}xpm run test-native-cmake-clang{% endif %}",
  "xpm run test-qemu-cortex-m0-cmake",
  "xpm run test-qemu-cortex-m3-cmake",
  "xpm run test-qemu-cortex-m7f-cmake"
],
"test-all": [
  "xpm run test-native-cmake",
  "xpm run test-cortex-cmake"
]
```

The `{% ... %}` parts are **Liquid** templates, evaluated by xpm with variables
such as `os.platform`. This is how the same manifest works on Linux, macOS and
Windows.

#### buildConfigurations

This is the matrix. Rather than repeating the platform, toolchain and build
type for every combination, the manifest uses **inheritance**: small hidden
building blocks are combined by name.

The hidden blocks are:

| Block | What it adds |
|---|---|
| `cmake-actions` | `prepare` (configure with toolchain), `build` (reconfigure + build), `test` (`ctest -V`), `clean` |
| `native-actions` | `install`, `link-deps` for native |
| `cortexm-actions` | `install`, `link-deps` for Cortex-M |
| `native-dependencies` | `@micro-os-plus/posix-arch`, `@xpack-3rd-party/libucontext` |
| `cortexm-dependencies` | `@micro-os-plus/micro-os-plus-iii-cortexm` |
| `arm-cmsis-dependencies` | `@xpacks/arm-cmsis` |
| `arm-none-eabi-gcc-dependencies` | the `arm-none-eabi-gcc` 14.2.1 toolchain |
| `gccNN-dependencies` | pinned GCC 11/12/13/14 toolchains |
| `clangNN-dependencies` | pinned clang 13…19 toolchains |
| `qemu-arm-dependencies` | the QEMU ARM emulator |
| `openocd-dependencies` | OpenOCD for physical boards |
| `short-win-paths-properties` | short build-folder names on Windows (path-length limit) |

A concrete configuration then looks like this:

```json
"qemu-cortex-m7f-cmake-debug": {
  "inherit": [
    "cortexm-actions",
    "cmake-actions",
    "cortexm-dependencies",
    "arm-cmsis-dependencies",
    "arm-none-eabi-gcc-dependencies",
    "qemu-arm-dependencies",
    "short-win-paths-properties"
  ],
  "properties": {
    "buildType": "Debug",
    "platformName": "qemu-cortex-m7f",
    "toolchainFileName": "arm-none-eabi-gcc.cmake",
    "shortConfigurationName": "m7fd"
  }
}
```

The release variant inherits the debug one and only overrides `buildType`:

```json
"qemu-cortex-m7f-cmake-release": {
  "inherit": ["qemu-cortex-m7f-cmake-debug"],
  "properties": {
    "buildType": "MinSizeRel",
    "shortConfigurationName": "m7fr"
  }
}
```

Note that release builds use **`MinSizeRel`** (`-Os`), not `Release`, on the
embedded targets.

## 6. Where the dependencies land

xpm installs packages in two places, and this is important to understand when
reading the CMake files:

1. **Top-level devDependencies** (from the main `devDependencies` block) go
   into `tests/xpacks/`:
   ```
   tests/xpacks/@micro-os-plus/build-helper
   tests/xpacks/@xpack-dev-tools/cmake
   tests/xpacks/@xpack-dev-tools/ninja-build
   tests/xpacks/@xpacks/arm-cmsis-rtos-validator
   tests/xpacks/@xpacks/chan-fatfs
   ```
   This is why `tests/CMakeLists.txt` can do
   `list(APPEND CMAKE_MODULE_PATH ".../tests/xpacks/@micro-os-plus/build-helper/cmake")`.

2. **Per-configuration devDependencies** (declared by the inherited
   dependency blocks) go into `tests/build/<configuration>/xpacks/`:
   ```
   tests/build/qemu-cortex-m7f-cmake-debug/xpacks/@micro-os-plus/micro-os-plus-iii-cortexm
   tests/build/qemu-cortex-m7f-cmake-debug/xpacks/@xpacks/arm-cmsis
   tests/build/native-cmake-gcc-debug/xpacks/@micro-os-plus/micro-os-plus-iii-posix-arch
   tests/build/native-cmake-gcc-debug/xpacks/@xpack-3rd-party/libucontext
   ```
   The platform `dependencies-folders.cmake` refers to these with
   `${CMAKE_BINARY_DIR}/xpacks/...`.

The toolchain binaries (compilers, QEMU, OpenOCD) are also installed under
`tests/build/<configuration>/xpacks/`, and xpm adds their `bin` folders to the
`PATH` for the duration of the action.

## 7. The CMake include chain

CMake is invoked from `tests/`, so `tests/CMakeLists.txt` is the entry point.
It runs a fixed sequence:

```
tests/CMakeLists.txt
 ├─ project(...)
 ├─ enable_language(C CXX ASM)
 ├─ set C11 / C++20 standards
 ├─ enable_testing()                         # turn on CTest
 ├─ append build-helper/cmake to CMAKE_MODULE_PATH
 ├─ include("micro-os-plus-build-helper")     # the xpack_* functions
 ├─ xpack_display_greetings(...)
 ├─ include("cmake/global-definitions.cmake") # ENABLE_*_TEST switches
 └─ include("cmake/tests-main.cmake")         # the real orchestration
```

### 7.1 `tests-main.cmake`

This is the generated orchestration file. In order it:

1. Enables `compile_commands.json` for IDEs.
2. Sets `.elf` as the executable suffix when cross-compiling
   (`CMAKE_SYSTEM_NAME STREQUAL "Generic"`).
3. Includes `cmake/common-options.cmake`, which defines the interface target
   `micro-os-plus::common-options` with the common warnings and flags.
4. Includes `platforms/${PLATFORM_NAME}/cmake/definitions.cmake`, which sets
   `xpack_platform_compile_definition`, `xpack_device_compile_definition`, and
   the linker script name.
5. Includes `platforms/${PLATFORM_NAME}/cmake/dependencies-folders.cmake`,
   which lists the folders to be added as subdirectories.
6. Calls `xpack_add_dependencies_subdirectories(...)`, which runs
   `add_subdirectory()` for each dependency folder listed in step 5. This is
   how `sources/rtos-apis`, the Cortex-M port, the CMSIS device and the
   filesystem all become part of the same build graph.
7. Calls `add_subdirectory(".." "top-bin")` — this adds the repository root
   `CMakeLists.txt`, defining the library target `micro-os-plus::iii`.
8. Calls `add_subdirectory("platforms/${PLATFORM_NAME}" "platform-bin")`,
   which defines the platform library and registers the test executables.

The key line is step 8: **the platform name alone selects everything else**.
`PLATFORM_NAME` arrives from the xpm action as `-D PLATFORM_NAME=...`.

### 7.2 `common-options.cmake`

Creates an interface library, `micro-os-plus-common-options-interface`, and its
alias `micro-os-plus::common-options`. It carries:

* compile definitions `DEBUG` and `TRACE` in Debug builds,
* `OS_USE_OS_APP_CONFIG_H` (tells the library to include the application
  config header),
* `-fmessage-length=0 -fsigned-char -ffunction-sections -fdata-sections`,
* the full warning set from `xpack_set_all_compiler_warnings()`.

Every test executable links this interface library, so all sources — including
the tested library — are compiled with the same options and warnings.

### 7.3 `global-definitions.cmake`

Simple on/off switches for the portable tests:

```cmake
set (ENABLE_RTOS_APIS_TEST true)
set (ENABLE_MUTEX_STRESS_TEST true)
set (ENABLE_CMSIS_OS_VALIDATOR_TEST true)
```

Individual platforms add their own (for example `nucleo-f411re` sets
`ENABLE_BLINKY_TEST` and `ENABLE_INSTRUMENTATION_TEST` in its
`definitions.cmake`).

### 7.4 The `xpack_*` helper functions

These come from `@micro-os-plus/build-helper/cmake/micro-os-plus-build-helper.cmake`:

| Function | Purpose |
|---|---|
| `xpack_add_dependencies_subdirectories(list binpath)` | `add_subdirectory()` each folder, failing if a `CMakeLists.txt` is missing. |
| `xpack_set_all_compiler_warnings(var)` | Builds a long list of warnings (`-Wall`, `-Wextra`, `-Wconversion`, `-Wshadow`, …) tuned per compiler and version. |
| `xpack_display_target_lists(target)` | Verbose dump of a target's includes, sources, definitions and options. |
| `xpack_display_greetings(package.json)` | Verbose banner with CMake/compiler/package versions. |
| `xpack_add_cross_custom_commands(target)` | POST_BUILD step that runs `size` on the ELF, and optionally `objcopy`/`objdump`. |
| `xpack_get_package_name_and_version(path)` | Reads `name` and `version` out of a `package.json` with CMake's JSON support. |

## 8. The CMake target graph

The build is entirely built from **INTERFACE libraries** — targets with no
compiled objects of their own that propagate sources, include folders,
definitions and options to whatever links them. This is what allows the same
source files to be compiled once per executable with the right flags.

The targets are:

| Target (alias) | Defined in | Carries |
|---|---|---|
| `micro-os-plus::iii` | root `CMakeLists.txt` | the whole portable library: `include/` and every file in `src/` |
| `micro-os-plus::common-options` | `tests/cmake/common-options.cmake` | warnings and common flags |
| `micro-os-plus::platform` | `platforms/<name>/cmake/platform-library.cmake` | platform include folder, CPU flags, linker script, `_POSIX_C_SOURCE`, and links to the port + device |
| `micro-os-plus::device` | `tests/device-qemu-cortexm/CMakeLists.txt` | startup, vectors, exception handlers and linker scripts for QEMU |
| `test::rtos-apis` | `tests/sources/rtos-apis/CMakeLists.txt` | the RTOS API test sources |
| `test::mutex-stress` | `tests/sources/mutex-stress/CMakeLists.txt` | the mutex stress test sources |
| `test::cmsis-os-validator` | `tests/sources/cmsis-os-validator/CMakeLists.txt` | (only the config header; the validator provides the code) |
| `test::blinky`, `test::instrumentation` | their `sources/` folders | platform-specific demos |
| `xpacks::chan-fatfs` | installed xPack | FAT file system |
| `xpacks::arm-cmsis-os-validator` | installed xPack | Arm CMSIS RTOS validator |
| `micro-os-plus::iii-cortexm` | installed xPack | Cortex-M scheduler port |
| `micro-os-plus::iii-posix-arch` | installed xPack | synthetic POSIX scheduler port |
| `xpack-3rd-party::libucontext` | installed xPack | ucontext support for the POSIX port |
| `xpacks::arm-cmsis` | installed xPack | CMSIS core headers |

Each test executable links a fixed set: the common options, the test library,
the tested library `micro-os-plus::iii`, any portable dependency, and the
platform library. For example the QEMU `rtos-apis-test` links:

```cmake
target_link_libraries (rtos-apis-test PRIVATE
  micro-os-plus::common-options
  test::rtos-apis
  micro-os-plus::iii
  xpacks::chan-fatfs
  micro-os-plus::platform
)
```

Because the platform library links `micro-os-plus::iii-cortexm` and
`micro-os-plus::device`, and the device links `xpacks::arm-cmsis`, the linker
command line ends up containing everything needed, with no manual ordering.

## 9. The test sources

The portable tests are plain programs with an `os_main()` entry point, not
`main()`. The library provides a weak default `main()` in
`src/rtos/os-main.cpp`: it prints the banner, starts the scheduler, and runs
`os_main()` on a dedicated µOS++ thread. That is why every test only has to
define `os_main()` and can use the RTOS API directly. The same test source is
compiled once per platform; only the platform glue changes.

### rtos-apis

The broadest test. `src/main.cpp` calls a series of test functions, each in its
own file:

* `test-cpp-api.cpp` — the C++ RTOS API,
* `test-c-api.c` — the C API,
* `test-iso-api.cpp` — the ISO C++ API (`std::thread`, `std::mutex`, …),
* `test-posix-io-api.cpp` — the POSIX I/O API,
* `test-chan-fatfs.cpp` — the FAT file system,
* `test-cmsis-os1.cpp` — the CMSIS-OS v1 compatibility API.

Each returns 0 on success. `main.cpp` stops at the first failure and returns
the error code, which becomes the process exit code and thus the CTest result.

### mutex-stress

Several threads contend for a mutex with random lock durations; the test
verifies the scheduling distribution is fair. It is designed to expose race
conditions that a simple functional test would miss.

### cmsis-os-validator

Wraps the Arm CMSIS RTOS API validator. The test folder contains only an
`os-app-config.h`; the actual validator code and `main` come from the
`@xpacks/arm-cmsis-rtos-validator` xPack.

### blinky and instrumentation

Platform-specific demos, enabled only where they make sense (the
`nucleo-f411re` board). `blinky` toggles the LED; `instrumentation` exercises
SEGGER SystemView tracing.

Every test folder provides its own `include/cmsis-plus/os-app-config.h`. This
is the application configuration header: it defines the system tick frequency,
stack sizes, memory pool sizes, which traces are enabled, and so on. The
`OS_USE_OS_APP_CONFIG_H` definition added by `common-options.cmake` is what
makes the library include it.

## 10. How a test is built and run

### 10.1 The native platform

`tests/platforms/native/CMakeLists.txt` creates a normal host executable and
registers it directly:

```cmake
add_test (NAME "rtos-apis-test" COMMAND rtos-apis-test)
```

CTest runs the binary as a process and uses its exit code. On Linux and macOS
the platform library also computes the compiler's runtime library paths and
adds `-Wl,-rpath,...` so the executable can find `libstdc++`/`libc++`.

### 10.2 The QEMU platforms

`tests/platforms/qemu-cortex-m7f/CMakeLists.txt` creates an ELF and registers
CTest to launch QEMU with semihosting:

```cmake
add_test (NAME "rtos-apis-test"
  COMMAND qemu-system-arm --machine mps2-an500 --cpu cortex-m7
          --kernel rtos-apis-test.elf --nographic
          -d unimp,guest_errors
          --semihosting-config enable=on,target=native,arg=rtos-apis-test)
```

`--semihosting-config enable=on,target=native` makes the guest's
semihosting calls (standard output and exit) go to the host. The QEMU process
therefore prints the test output and exits with the guest's exit code, which is
exactly what CTest needs. The mapping is:

| Platform | Machine | CPU | Linker script |
|---|---|---|---|
| `qemu-cortex-m0` | `mps2-an385` | `cortex-m3` | `mem-mps2-an385.ld` |
| `qemu-cortex-m3` | `mps2-an385` | `cortex-m3` | `mem-mps2-an385.ld` |
| `qemu-cortex-m4f` | `mps2-an386` | `cortex-m4` | `mem-mps2-an386.ld` |
| `qemu-cortex-m7f` | `mps2-an500` | `cortex-m7` | `mem-mps2-an500.ld` |

The M0 configuration is run on the `mps2-an385` machine with the Cortex-M3 CPU
because QEMU has no separate M0 board; the code is still compiled for
`cortex-m0`.

### 10.3 The physical boards

For the NUCLEO boards and the Raspberry Pi Pico, CTest launches **OpenOCD**,
which programs the flash and starts execution:

```cmake
add_test (NAME "rtos-apis-test"
  COMMAND openocd -c "gdb port disabled" -c "tcl port disabled"
          -f interface/stlink-dap.cfg -f target/stm32f4x.cfg
          -c "program rtos-apis-test.elf verify"
          -c "arm semihosting enable"
          -c "arm semihosting_cmdline rtos-apis-test"
          -c "reset")
```

Semihosting again carries the output and the exit code back to the host over
the debug probe. The Pico uses a different OpenOCD configuration and a
`rp2040.core0 arp_reset assert 0` sequence to release the core after reset.

### 10.4 The build sequence

For any configuration, the actions do the following:

1. `prepare` — `cmake -S . -B build/<config> -G Ninja -D CMAKE_BUILD_TYPE=... -D PLATFORM_NAME=... --log-level=VERBOSE` plus
   `-D CMAKE_TOOLCHAIN_FILE=xpacks/@micro-os-plus/build-helper/cmake/toolchains/<file>`.
2. `build` — re-run the configure step, then `cmake --build build/<config>`.
3. `test` — `cd build/<config> && ctest -V`.
4. `clean` — `cmake --build build/<config> --target clean`.

The toolchain files set the compilers and, for cross builds, the
`CMAKE_SYSTEM_NAME Generic` / `CMAKE_SYSTEM_PROCESSOR arm` pair that marks the
build as cross-compilation.

## 12. Continuous integration

The GitHub Actions workflow is `.github/workflows/ci.yml`. It runs on a matrix
of operating systems:

```yaml
os: [ 'ubuntu-24.04', 'ubuntu-24.04-arm', 'macos-15-intel', 'macos-15', 'windows-2025' ]
```

and does four things:

1. Checks out the repository.
2. Installs Node.js 22 and `xpm@0.20.8`.
3. `npm --prefix tests ci` — installs the JavaScript devDependencies
   (`del-cli`) from `tests/package-lock.json`.
4. `xpm run install-ci -C tests` — installs the xPack dependencies for the
   configurations relevant to that OS.
5. `xpm run test-ci -C tests` — runs the tests.

`install-ci` and `test-ci` are Liquid-templated, so each operating system
installs and runs only what it can:

* Linux runs native GCC and clang, plus QEMU M0/M3/M7.
* macOS runs native clang, plus QEMU M0/M3/M7.
* Windows runs the QEMU Cortex-M targets.

The README also mentions a second, manually triggered workflow (`test-all.yml`)
that is intended to run every test on every supported platform; in the current
branch that file is not present, and `xpm run test-all` is the local
equivalent.

The CI workflow ignores documentation-only changes (`**.md`, `docs/**`,
`doxygen/**`, …) through `paths-ignore`, so a docs edit does not trigger a
build. It also uses `concurrency` with `cancel-in-progress: true`, so pushing a
new commit cancels the previous run for the same branch.

## 13. Extending the framework

### Add a portable test

1. Create `tests/sources/<name>/` with a `CMakeLists.txt` that defines an
   interface library and an alias `test::<name>`, following the pattern of
   `sources/mutex-stress/`.
2. Add the sources and its `include/cmsis-plus/os-app-config.h`.
3. Add an `ENABLE_<NAME>_TEST` switch in `tests/cmake/global-definitions.cmake`
   (or a platform `definitions.cmake`).
4. Add the folder to each platform's `dependencies-folders.cmake`.
5. Register the executable and `add_test()` in each platform's
   `CMakeLists.txt`.

### Add a platform

1. Create `tests/platforms/<name>/` with:
   * `CMakeLists.txt` (the test executables and `add_test()` commands),
   * `cmake/definitions.cmake` (device and platform compile definitions,
     linker script name, platform-specific test switches),
   * `cmake/dependencies-folders.cmake` (the folders to add),
   * `cmake/platform-library.cmake` (the `micro-os-plus::platform` interface
     library),
   * `include/cmsis-plus/platform.h`.
2. Add a `buildConfigurations` entry (or a family of entries) in
   `tests/package.json`, inheriting the appropriate hidden blocks and setting
   `platformName` and `toolchainFileName`.
3. Add aggregate `test-<name>-cmake` actions if desired.

### Add a toolchain version

Add a hidden `gccNN-dependencies` / `clangNN-dependencies` block pinning the
xPack tool, then a configuration that inherits it. No CMake changes are
needed because the toolchain file name is already a property.

## 15. Why it is built this way

A few design decisions explain most of the structure:

* **Interface libraries everywhere.** Because every component is an INTERFACE
  library, the *same* source file can be compiled into many executables with
  different flags, without duplicating files or maintaining lists of objects.
* **One `PLATFORM_NAME` switch.** The platform name selects the definitions,
  the dependencies and the executables. There is no `if(OS)` branching in the
  top-level scripts.
* **Pinned tools as xPacks.** Every compiler, QEMU and OpenOCD comes from an
  xPack devDependency, so a developer's machine and CI use identical versions,
  and nothing has to be installed globally.
* **The matrix lives in `package.json`.** Adding a platform or a toolchain is a
  JSON edit, not a change to the build logic.
* **CTest is the common interface.** Whether the test runs as a native
  process, in QEMU, or on a physical board via OpenOCD, the result is still a
  CTest pass/fail with the program's output, so the aggregate actions are just
  lists of `ctest -V` calls.

## 16. From reset to `os_main`

A test defines `os_main()`, not `main()`. The entire boot path that reaches it
is supplied by the library and the device package.

The sequence on a Cortex-M target is:

1. **Reset.** The CPU loads the initial stack pointer and `Reset_Handler` from
   the first two entries of `_interrupt_vectors[]`, the table defined in
   `tests/device-qemu-cortexm/src/vectors-cortexm.c` (or the equivalent
   `vectors_*.c` in a board's device folder). The table lives in the
   `.isr_vector` section, which the linker places at the start of flash.
2. **`Reset_Handler` → `_start`.** `Reset_Handler`, in
   `src/startup/exception-handlers.c`, calls `_start`, implemented in
   `src/startup/startup.cpp`.
3. **`_start`** performs, in order:
   * `os_startup_initialize_hardware_early()` — a weak hook implemented in
     `src/startup/initialize-hardware.c`. It calls the CMSIS `SystemInit()`
     (and `SystemClock_Config()` when `OS_HAS_SYSTEMCLOCK_CONFIG` is defined),
     then sets `SCB->VTOR` to the real vector table address.
   * copy `.data` from flash to RAM and clear `.bss` (or use the multi-region
     arrays when `OS_INCLUDE_STARTUP_INIT_MULTIPLE_RAM_SECTIONS` is defined).
   * `os_startup_initialize_hardware()` — a second weak hook; on QEMU it only
     calls `SystemCoreClockUpdate()`, on boards it initialises the clocks.
   * `os_startup_initialize_free_store()` — sets up the heap.
   * `os_startup_initialize_args()` — builds `argc`/`argv`; on embedded targets
     it can take them from semihosting.
   * run the preinit and init arrays, i.e. the C++ static constructors.
   * call `main(argc, argv)`.
4. **`main()`.** This is the library's weak default in
   `src/rtos/os-main.cpp`. It prints the µOS++ banner, creates a µOS++ thread
   with the stack size from `OS_INTEGER_RTOS_MAIN_STACK_SIZE_BYTES`, and starts
   the scheduler. The thread's trampoline prints the arguments, calls
   `os_main(argc, argv)`, and then calls `std::exit(code)`.
5. **Exit.** `std::exit()` runs the `atexit()` handlers and static
   destructors, then calls `_exit()`, which on an embedded target issues a
   semihosting `SYS_EXIT` with the code.

Because the reset vector, the startup code and `main()` all come from the
library, a test file only has to provide `os_main()`; nothing platform-specific
has to be written.

The **device package** is the part that differs per board:

| Platform | Device sources |
|---|---|
| `qemu-cortex-m0/m3/m4f/m7f` | `tests/device-qemu-cortexm/` (generic QEMU device) |
| `nucleo-f411re` | `tests/platforms/nucleo-f411re/device/` + `stm32f411cubemx/` |
| `nucleo-f767zi` | `tests/platforms/nucleo-f767zi/device/` |
| `nucleo-h743zi` | `tests/platforms/nucleo-h743zi/device/` |
| `raspberrypi-pico` | `tests/platforms/raspberrypi-pico/device/` + `src/bs2_default_padded_checksummed.S` |

The QEMU device is deliberately minimal: a 16 MHz `SystemCoreClock`, an FPU
enable in `SystemInit()`, a generic vector table, and a SysTick handler that
calls `os_systick_handler()`. The board devices add the CubeMX-generated
`system_stm32*.c`, the real vector tables, and the STM32 HAL sources. All of
them become the `micro-os-plus::device` interface library.

## 17. Tracing and how test output reaches the host

Two mechanisms carry text out of the target: the µOS++ **trace** facility and
the **newlib retargeting** of `printf`.

### The trace facility

The core is `src/diag/trace.cpp`, compiled only when the `TRACE` macro is
defined — which `common-options.cmake` does for Debug builds. It provides
`os::trace::printf()`, `write()` and `flush()`, plus the C alias
`trace_printf()`.

The actual backend is chosen at compile time:

| Macro | Backend file | Used by |
|---|---|---|
| `OS_USE_TRACE_SEMIHOSTING_STDOUT` | `src/diag/trace-semihosting.cpp` | QEMU and board tests |
| `OS_USE_TRACE_SEGGER_RTT` | `src/diag/trace-segger-rtt.cpp` | SEGGER RTT (instrumentation) |
| `OS_USE_TRACE_ITM` | `src/diag/trace-itm.cpp` | SWO/ITM debug output |
| (none) | `src/diag/trace.cpp` weak fallback | disabled output |

Each platform's `CMakeLists.txt` sets the macro on the test executable. For
example, the QEMU platform adds:

```cmake
target_compile_definitions (${name} PRIVATE OS_USE_TRACE_SEMIHOSTING_STDOUT)
```

while the native platform adds `OS_USE_TRACE_POSIX_STDOUT`, which writes
through the POSIX I/O layer to the host's standard output.

### Newlib retargeting

The library also provides the C library system calls, so ordinary `printf()`
works:

* On embedded targets, `src/semihosting/c-syscalls-semihosting.cpp` implements
  `_write`, `_read`, `_exit`, `_sbrk` and friends with semihosting calls.
* On native targets, `src/libc/_sbrk.c`, `src/libc/stdlib/*` and
  `src/posix-io/c-syscalls-posix.cpp` provide the POSIX equivalents.

### How the result gets back

The chain is short and uniform:

```
os_main() returns int
   └─ main trampoline calls std::exit(code)
        └─ _exit(code)
             └─ semihosting SYS_EXIT          (embedded)
                or process exit               (native)
                  └─ QEMU / OpenOCD exits with that code
                       └─ CTest records pass or fail
```

The `--semihosting-config ...arg=<name>` value becomes `argv[0]`, which the
trampoline prints with `trace::dump_args()`, so the CTest log shows which test
ran. Nothing else is needed for CTest to decide the outcome.

## 18. Memory layout and linker scripts

Each device supplies two linker scripts, both passed with `-T` through
`micro-os-plus::device`:

* `mem-<board>.ld` — the `MEMORY` block (flash and RAM origins and lengths).
* `sections-flash.ld` — the `SECTIONS` block: where the vector table, the
  init/fini arrays, `.text`, `.data`, `.bss`, `.noinit` and the stack check
  live.

The link uses `-nostartfiles` (so the library's own `_start` is used instead of
the toolchain startup) and `-Wl,--gc-sections` (so unused code is dropped).
From GCC 12 the platform library also adds `-Wl,--no-warn-rwx-segment`.

The QEMU memory maps are:

| Platform | FLASH | RAM | PSRAM (heap) |
|---|---|---|---|
| `qemu-cortex-m0` | 0x00000000, 8 MB | 0x20000000, 8 MB | 0x21000000, 16 MB |
| `qemu-cortex-m3` | 0x00000000, 8 MB | 0x20000000, 8 MB | 0x21000000, 16 MB |
| `qemu-cortex-m4f` | 0x00000000, 8 MB | 0x20000000, 8 MB | 0x60000000, 16 MB |
| `qemu-cortex-m7f` | 0x00000000, 8 MB | 0x20000000, 8 MB | 0x60000000, 16 MB |

The PSRAM region exists because the QEMU startup asks semihosting for
`SYS_HEAPINFO` and places the heap and stack at the addresses QEMU reports; the
`PSRAM` region simply reserves that space in the map. The physical boards use
their own memory maps — for instance the Raspberry Pi Pico has 2 MB of flash at
0x10000000 and 256 KB of RAM at 0x20000000.

After linking, `xpack_add_cross_custom_commands()` always runs `size` on the
ELF, and can optionally run `objcopy` (hex) and `objdump` (listing) when the
`xpack_create_hex` / `xpack_create_listing` variables are set.

## 19. The instrumented test and the board demos

Two test sources are board-specific and are only built where they make sense.

### instrumentation

Enabled on `nucleo-f411re` through `ENABLE_INSTRUMENTATION_TEST` in that
platform's `definitions.cmake`. It exercises SEGGER SystemView. The platform
builds two images:

* `instrumentation-test` — a simple case,
* `rtos-apis-instrumentation-test` — the full RTOS API test with
  instrumentation enabled.

Both define `OS_HAS_SYSTEMCLOCK_CONFIG`, `OS_USE_TRACE_SEMIHOSTING_STDOUT` and
`OS_INCLUDE_INSTRUMENTATION`, and link the `segger::rtt` and
`segger::system-view` targets, which come from the `@xpack-segger/rtt` and
`@xpack-segger/system-view` devDependencies.

There is **no automated CTest entry** for these images: SystemView requires the
SEGGER desktop tools and a J-Link. The platform folder ships the project files
used for manual sessions (`instrumentation.jdebug`, `instrumentation.SVPrj`,
`rtos-api-test-instrumentation.jdebug`).

### blinky

Also `nucleo-f411re`-only, enabled by `ENABLE_BLINKY_TEST`. It toggles the
board LED; the OpenOCD test passes two arguments (the on and off times in
milliseconds) through `arm semihosting_cmdline`.

## 20. Code style, formatting and editor integration

The project enforces a consistent style with three tools, all configured from
the `config/` folder:

* **clang-format** — `config/.clang-format` (and the root `.clang-format`)
  uses `BasedOnStyle: GNU` with C++20. The action `clang-format` runs
  `scripts/clang-format.sh`, which formats `src/`, `include/`,
  `tests/sources/` and `tests/platforms/`.
* **cmake-format** — `config/.cmake-format.py` sets a 2-space indent, an
  80-column width and `dangle_parens`. The action `cmake-format` runs
  `scripts/cmake-format.sh` over every `CMakeLists.txt` and `*.cmake`, skipping
  `build/`, `xpacks/` and `node_modules/`.
* **prettier** — `config/.prettierrc.json` and `config/.prettierignore` cover
  the JavaScript/JSON files (for example the `package.json` files).

Both formatting actions are declared in the **root** `package.json`, so they
are run from the repository root:

```sh
xpm run clang-format
xpm run cmake-format
```

For editing, the repository ships VS Code support. `.vscode/launch.json`
contains `cppdbg` launch configurations for the native test executables, with
the xPack tool folders added to `PATH` and `LD_LIBRARY_PATH` so the debugger
finds the right runtime. `.vscode/settings.json` excludes the generated and
third-party trees from indexing (`xpack.exclude`, `npm.exclude`) and adds the
project's spelling dictionary. With the xPack VS Code extension installed, the
xpm actions appear as buttons, so the same `prepare`/`build`/`test` steps can be
run without typing commands.

## 22. Known limitations and caveats

The maintainers' notes in `tests/TO-CHECK.md` and `tests/README.md` record a
few things worth knowing:

* **No trace output in the scheduler interrupt handler.** If trace prints
  happen inside the scheduler ISR, the tests occasionally fail — less often
  under emulation, almost always on physical boards. This is why the
  `rtos-apis` `os-app-config.h` leaves `OS_TRACE_RTOS_SCHEDULER` commented out.
  With that discipline the tests have run for many hours in loops without
  problems.
* **Historical release-build failures.** Some macOS release runs of
  `rtos-apis-test` were recorded as `Illegal instruction` or `SegFault`; these
  were noted but not yet investigated, and debug builds pass.
* **The manual `test-all.yml` workflow is not in the branch.** The README
  refers to it, but only `ci.yml` exists; `xpm run test-all` is the local
  equivalent.
* **No Cortex-M0 machine in QEMU.** The `qemu-cortex-m0` configuration compiles
  for `cortex-m0` but runs on the `mps2-an385` (Cortex-M3) machine.
* **Physical-board tests are manual.** They require the board and a debug probe
  (ST-Link or CMSIS-DAP), so they are not part of CI.

## 23. The wider xPack ecosystem

The tests do not exercise a self-contained library. The portable
`micro-os-plus-iii` is combined with a port, a device and third-party xPacks,
all pinned in `tests/package.json`:

| xPack | Version | Role |
|---|---|---|
| `@micro-os-plus/micro-os-plus-iii-cortexm` | v1.1.0 | Cortex-M scheduler port |
| `@micro-os-plus/posix-arch` | v1.0.1 | synthetic POSIX scheduler port |
| `@xpack-3rd-party/libucontext` | v1.2.0-5 | ucontext support for the POSIX port |

| `@micro-os-plus/build-helper` | ^2.17.0 | CMake functions and toolchain files |

The **build-helper** is the shared infrastructure package. Besides the
`xpack_*` functions used by the CMake scripts, it ships toolchain files for
several architectures:

```
cmake/toolchains/gcc.cmake
cmake/toolchains/clang.cmake
cmake/toolchains/arm-none-eabi-gcc.cmake
cmake/toolchains/aarch64-none-elf-gcc.cmake
cmake/toolchains/riscv-none-elf-gcc.cmake
```

Only `gcc.cmake`, `clang.cmake` and `arm-none-eabi-gcc.cmake` are used on this

provides developer scripts (`dev-scripts/get-libraries-paths.sh`, used for the
native RPATH, and the `git-*` helpers).

On Linux, `"local": "link"` makes xpm link each package to its copy in the
central store (`~/.local/xPacks/...`) instead of copying files. The
`tests/package.json` actions `git-clone-deps`, `git-pull-deps` and
`link-deps` exist so a developer can clone the dependency repositories under
`$HOME/Work` and work on them in place, then have the tests use those working
copies.

| **build configuration** | platform + toolchain + build type; owns a build folder. |
| **CTest** | CMake's test runner; `add_test()` registers, `ctest` runs. |
| **interface library** | A CMake target that only propagates usage requirements. |
| **xPack** | The package format used by xpm. |
| **xpm** | The Node.js package/build manager for C/C++ projects. |
| **semihosting** | A debug protocol that lets the target use the host's I/O. |
| **toolchain file** | A CMake file that selects the compilers for cross builds. |
